# 荔枝 App · Windows 与 Android 多端实施方案

2026 年 11 月 25 日｜正式方案 V1.1｜供项目负责人、开发者和真机验收者使用

> **2026 年 11 月 25 日 · Windows 执行口径更新**  
> 根据负责人最新决定，Windows 新版以移动 V6.3.3 的界面、功能及原画为基准，单独交付可删除的试用目录。宽窗和小窗分别适配，直接进入荔枝应用。原 Windows v4.1.7 的程序、启动入口和更新渠道继续独立保留。下文涉及从原渠道升级、覆盖或替换旧服务的步骤暂停执行。先用临时账号验证视觉和操作；正式账号的跨端同步另行验收。Windows 优先，其次 Android APK，最后 iOS。

## 1. 目标、范围与完成定义

以移动版 V6.3.3 为功能和美术基准，延续 Windows 4.1.7 的桌面体验，让用户在 Android、Windows 及现有手机 PWA 上使用原账号处理同一份业务数据。各端使用统一的产品版本和更新说明，Windows、Android 安装包分别记录升级所需的内部构建号。用户在手机创建提醒，回到电脑即可处理；从手机养大的树，在电脑上继续照料。这两个场景分别验证个人数据和多人互动。

| 对象 | 本期决定 | 完成标准 |
|---|---|---|
| Windows | 保留 C / WebView2 桌面壳，分别设计小窗与展开布局 | 老用户可由原渠道升级，置顶、缩放、快捷隐藏、托盘、旧有聊天和游戏可用，能使用迁入的移动功能 |
| Android | 在 Windows 上开发和构建，以 Capacitor 封装现有移动前端，优先交付可直接安装的 APK | Android 实机完成安装、登录、重启、核心功能操作及覆盖升级；提交商店另行决定 |
| 手机 PWA | 老用户继续从原地址或主屏幕打开，包括 iPhone | 原账号和历史数据可读，与新端双向同步 |
| 荔枝树 | 新 Windows 庭院统一接入移动端规则和记录，放弃旧桌面果园进度 | 有新版记录的账号见到原树，新用户按新版规则从小苗开始；已长成的果实才可赠送 |
| 以后再做 | iOS 原生壳、Codemagic、App Store、独立 CDN 和域名调整 | 本期的构建、测试及发布均无须采购这些服务 |

本期交付包括桌面更新、Android 安装包、可重复构建的工程、可回退的发布记录和实测结果。每一端分别记录代码、本地测试、真实接口、构建、部署或分发、真机验收六类状态。

## 2. 开发起点和已有证据

- 手机原入口核查时返回 6.3.3；V6.3.3 交接包的发布分片解码与 SHA-256 复算一致。包内有服务端模块、构建后的 JS/CSS、部分静态资源及设计稿。完整开发入口、依赖和基础资源仍需补齐。
- 桌面线上清单返回产品版本 4.1.7、Windows 构建号 3。本机找到使用 WebView2 且指向原服务的 exe；它与线上可下载 exe 是否为同一文件尚待比对。交接包的桌面渲染代码可用于对照；对应 C、原始 TS/TSX 及构建脚本仍待找回。
- 手机与桌面渲染层均有 /api/account 和 /api/camp；手机另用 /api/phone 等接口。服务有会话与同源检查。已有共同入口，仍须用实测确认各模块的数据归属、查看权限及刷新时机。
- 原服务运行 Node.js，数据库为 Turso/libSQL。Render 当前关联示例仓库，实际发布还依赖启动基线、代码分片与归档资源，单独拉取示例仓库无法重建荔枝。以后可在得到授权后用独立私有仓库保存无密钥的可构建项目。
- Seedream 曾真实生成 2048 × 2048 JPEG；DeepSeek 有中文、思考与联网返回来源的既有探测。证据属于对应历史版本。新客户端的展示、额度、保存和设备操作仍需验收。

原资料为移动版 V6.3.3 交接包。公开仓库的历史资料见版本清单。 · [手机原入口](https://lychee-link-check.onrender.com/mobile/) · [桌面线上发布清单](https://lychee-link-check.onrender.com/app-version.json)

## 3. 产品功能与端上分工

| 功能 | Windows | Android 与 PWA | 共用的业务规则 |
|---|---|---|---|
| 账号、头像、状态 | 展开页编辑，聊天和成员列表统一显示头像 | 沿用个人卡片，相册或 AI 头像保存后预览 | 按账号读取新版头像；旧预设头像可回退，切号后清理上一账号的缓存 |
| 提醒、循环、约定、倒计时 | 小窗看最近一项，展开页管理列表、编辑和完成 | 复用移动布局，核对键盘、日期选择和前后台恢复 | 服务端记录归属、时刻、循环规则和完成状态；各端本地刷新秒数 |
| 记事本、园中事、我的状态、账本、番茄钟 | 按清单补齐入口；列表与详情适配鼠标键盘 | 复用现有工具，核对打开、编辑、保存和返回 | 逐项区分账号记录与设备偏好。先查明草稿或计时状态原有保存位置 |
| AI 助手、AI 生图 | 历史侧栏、对话或画布主区、选择参考图、保存文件 | 测试软键盘、参考图、结果预览、保存和设为头像 | 服务端统一处理鉴权、额度、历史及模型密钥；切换设备不会重复提交同一请求 |
| 小队聊天、问一问、五子棋及其他旧游戏 | 先保护原有入口，再适配宽屏、输入焦点及观战 | 检查键盘、返回和切后台重连 | 消息、成员权限和棋局沿用已核实的数据来源；重复发送、断线重连须测试 |
| 荔枝树、赠果、留言 | 使用新版庭院美术与规则，左侧可呈现场景，右侧呈现照料与收礼 | 继续使用已确认的移动庭院及手记 | 同一棵树、同一批果实。赠送要扣减成熟果实，留言按收件权限读取 |

设计以已有页面、八幅庭院场景和移动设计稿为准。新桌面布局先审两张可操作的页面样例：悬浮便签与展开后的提醒详情。Windows 小窗应在工作时一眼看清，展开后适合多项管理。窄窗、不同显示缩放、鼠标滚轮、Tab/Enter/Esc、恢复窗口位置均列入体验检查。Android 重点看系统返回、键盘遮挡、系统栏安全区、系统字号、相册取消和权限被拒后的恢复。

## 4. 架构与数据约定

1. 保留现有 Node 服务、Turso、原域名和 PWA 路径。先列出每项功能的接口、用户身份、所属记录、读写权限及原版本调用方式。新增接口或字段保持向后兼容，原 Windows 和 PWA 可继续访问。
2. 移动网页前端产出可独立构建的静态目录。PWA 继续按原路径加载；Android 把入口及首屏资源打进 APK，通过明确的服务地址访问后端。核对绝对 /mobile/ 路径、字体图片、懒加载资源和下载链接。冷启动时先显示荔枝页面，后端休眠时显示连接状态和重试入口。
3. 每项公共功能维护一份主要实现。例如 Windows 展开页、Android 和 PWA 共用提醒编辑器、重复选项和保存流程，服务端统一校验和写入。Windows 小窗可单独显示最近一项，手机可调整按钮布局。其他功能迁入第二端时沿用此做法。Windows 原生桥负责窗口和托盘；Android 适配层负责文件、分享和系统返回。前端无需持有数据库或模型供应商密钥。
4. Android 的首项技术验证是登录。核对本地应用来源、请求地址、Cookie 或现有令牌、会话过期、退出及服务端同源检查。优先验证现有机制；若需新增移动会话，只限定受支持的来源和权限，保留原网页保护。PWA 与首次安装的 APK 可分别登录同一账号，验收以登录后能延续原数据为准。
5. 用账号同步业务记录。窗口位置、设备权限等留在设备；离线时保留输入并明确待提交状态。对采摘、赠果、发送和计费请求，先核查现有防重行为，再补足防重与失败恢复。业务成功以服务端确认结果为准。

## 5. 荔枝树切换规范

移动端新版庭院是新客户端唯一读写的业务来源。已发现新庭院使用 yard65_*，旧果园含 orchard_*。实施时沿用现有新版接口，在隔离数据上核实实际账号、庭院、果实和收件人的关联。

| 账号或操作 | 新版 Windows 的行为 | 验收证据 |
|---|---|---|
| 手机已有树，桌面也有旧树 | 读取手机树的阶段、照料记录、成熟果、赠送与收件记录，旧桌面进度不计入 | 两端对照同一账号；打开新版桌面前后，手机记录及果实数量一致 |
| 只有旧桌面树 | 首次按移动端已有规则建树，从小树苗开始；即使旧树已成熟也不能直接领果 | 首次进入和重新登录后均为同一棵新树，无额外果实 |
| 桌面与手机同时首次进入、采摘或赠送 | 建树只生效一次，同一果实只能被有效采摘、赠送一次 | 同时操作及网络重试后，树、果实数量、收件记录一致 |
| 赠送留言荔枝 | 先获得成熟果，选收件人并附留言；收件端用既有醒目标记提醒，点开查看 | 发送者扣减一次、收件人收取一次、第三个账号无法读取私人留言 |
| 切换失败或回退客户端 | 保留新版已经产生的照料、采摘和收件记录。在修复前可继续用手机查看新版庭院 | 回退演练前后比对新版记录，手机仍可读；如旧客户端显示旧果园，两套进度各自隔离 |

切换只涉及 Windows 果园入口及其数据来源。本次发布保留旧表，避免误伤共用的账号、聊天和小游戏。桌面首次进入新版可用一行提示说明“荔枝树现已和手机版同步”，减少老用户看到小苗时的疑惑。

## 6. 实施顺序与放行条件

| 阶段 | 工作与产物 | 放行条件 |
|---|---|---|
| A　恢复构建基线 | 找回原始工程，整理前端、C 壳、依赖版本、启动脚本、资源来源、公开配置样例和原发布物摘要。在干净目录重建手机前端和 Windows exe；记录可解释的编译差异 | 能本地启动、定位原入口、核对关键资源并恢复旧版。找不到 Windows 原工程时，桌面壳改动暂停，Android 与手机构建核对可继续；如需重建桌面工程，另评估范围 |
| B　Windows 提醒试点 | 在隔离环境贯通登录、查看、编辑、完成、循环与同步，提供悬浮小窗和展开页。保留旧桌面设置与原生桥 | 手机建提醒，电脑完成，手机刷新后可见；两端重启仍一致，另一账号读不到。旧版窗口操作回归通过 |
| C　Android 首个真机包 | 准备兼容的 Node、JDK、Android SDK 与 Gradle；配置稳定应用标识、移动构建目录和服务地址，执行前端构建、Capacitor 同步、APK 编译并安装到真机 | 在真实手机上冷启动、登录、重启、退出、重登并完成同一条提醒。验证返回键、键盘遮挡、断网、后端唤醒及选图。开发测试包与可长期升级的签名包分别登记 |
| D　扩展主要功能 | 首批个人资料、约定和工具箱；次批园中事、AI 及图片；再做社交、游戏和庭院。旧功能已满足要求时只回归，无须重写 | 各批至少有跨端读写、权限、失败恢复三类证据；AI 另列模拟响应与经授权的真实接口结果；庭院按第 5 节验收 |
| E　兼容发布、分发与回退 | 固定版本和摘要，演练旧版升级及回退。先让后端支持新旧端，再分发 Windows 候选包与 Android 签名 APK，负责人真机验收后推广 | 旧 PWA、Windows 4.1.7 与新端可并存；原入口可用，覆盖安装保留业务数据，真实设备通过后记录正式发布 |

**开工先验证两件事。** ① 用现有源码和依赖实际构建移动前端和 Windows 程序，记下能运行的入口和缺失文件。Windows 原工程暂缺时，先推进移动前端和 Android 首包。② 第一个 APK 装上真机后，立即用已有提醒的测试账号登录，打开并修改这条提醒，在电脑上刷新核对。新版 Windows 入口尚未就绪时，可先用电脑浏览器核对写入；待桌面入口就绪，再用 Windows 客户端正式验收。

**再验证一次后续更新。** 提醒跑通后，选一个各端都需要、当前还没有的小改动，例如加一个“推迟十分钟”的选项。在共用提醒模块中实现一次，留存改动文件清单。分别在 Windows、更新后的 Android APK 和 iPhone 的 PWA 上操作，核对修改后的提醒时间能同步到其他端。通过后再扩展其余模块。更新说明写明哪些改动随服务上线生效、哪些需要刷新网页或安装新版。

原生推送、后台定时提醒若要承诺“杀掉 App 仍准时到达”，需另列权限、系统限制和设备验证；首轮先验证提醒数据和现有功能。

## 7. 验收、发布与回退

| 检查 | 最小用例 | 留存证据 |
|---|---|---|
| 身份与隔离 | 两个隔离测试账号，分别在 Windows、Android、PWA 登录，交叉检查个人提醒、AI 历史和私人留言 | 客户端版本、设备、操作步骤、预期及实际结果，证据去除账号敏感信息 |

| 桌面回归 | 从 4.1.7 覆盖升级，验证原小窗、置顶、缩放、托盘、快捷隐藏、聊天及游戏；核对网页与原生壳版本搭配 | 旧新版本、文件摘要、更新清单校验、升级结果和可用回退包 |
| Android 更新 | 选择能长期使用的应用标识和发布签名，用同签名、更高版本号的候选包覆盖上一包，检查会话、头像和本地偏好 | 两个已签名包的版本号、安装结果、真机型号及 Android 版本；签名私钥由项目负责人保管 |
| AI 与图片 | 验证中文问答、思考、联网来源、历史隔离；真实生图后分别验证预览、保存和头像应用 | 将模拟、真实供应商返回和真机结果分开登记。复用一次有效生成结果覆盖后续设备操作，控制费用 |
| 发布与恢复 | 保留原始分片、基线、摘要和回退物；同一 Render 服务覆盖更新。验证旧入口、已发布客户端和新数据的可读性 | 部署编号、版本入口、关键只读探测、真机签收。发现登录普遍失败、数据串号、重复扣果或更新失败即停止推广 |

**按影响安排修复。** 按钮位置、小窗大小、键盘遮挡等，等有了可用版本再边试边调。如果遮挡导致无法保存，就在该功能验收时修好。账号能否读到别人的私人记录、断网重试会不会重复扣果或送果，在对应功能完成后测试，正式发布前必须通过。

数据库采用兼容性改动。代码回退优先恢复上一个可用服务版本或关闭新增入口；保留上线后新增的真实用户记录。Android 回退应准备版本号更高、内含已知稳定代码且使用同一签名的修复包，减少卸载导致本地状态丢失。Windows 回退须事先验证现有更新器的版本和清单规则，再确定修复包构建号。测试优先使用本地或已授权的隔离数据；写生产、发布、采购或新增付费调用按相应授权执行。

每个发布项记录六栏：代码改动、本地测试、真实 API、构建产物、部署或分发、真机验收。每栏填“通过、失败、待测或不适用”，附版本和证据。例如 Render 为 live 只能填写部署栏，APK 构建成功只能填写构建栏。

## 8. 工作量、责任与下一步

以下为单人净开发粗估，假设原工程可找回、现有服务可继续使用，Android 首发通过 APK 分发。范围覆盖实施、测试和发布准备；不含找不到源码后的重建、商店审核等待、iOS、CDN、额外美术重制或商业服务采购。

| 工作 | 粗估 |
|---|---:|
| A　基线恢复与回退核对 | 2–5 人日 |
| B　Windows 提醒试点 | 3–6 人日 |
| C　Android 首包、鉴权与真机试用 | 3–7 人日 |
| D–E　其余模块、庭院切换、回归、发布与升级验证 | 15–35 人日 |
| 合计 | **23–53 人日** |

最大的误差来自桌面原工程缺失和旧账号兼容。放弃旧果园记录可省去历史换算与合并；双端并发和已送留言的权限验证仍要保留。完成 Windows 与 Android 提醒试点后，用实际耗时和逐模块差异重新估算。

开发执行者负责集成、构建、测试、整理发布证据和回退演练。项目负责人 Wayne 决定重大产品取舍、费用、正式发布及实机体验是否通过。每阶段交付一份简短状态，列出用户能用什么、验证到哪一步、发现什么问题以及是否可以进入下一阶段。

首项交付为“可重复构建的基线”：原工程位置、构建命令与依赖、旧发布物和本地构建结果、仍待找回项、回退入口。首个功能交付为三端提醒试点。Windows 原工程未找齐时，明确标记桌面构建缺口；移动基线和 Android 试点可独立推进。
