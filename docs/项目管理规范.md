# 荔枝项目管理规范

从[根目录接手入口](../AGENTS.md)进入。项目负责人决定目标、优先级和采用的版本。每项任务指定一位主写人；只有一个执行者时，由该执行者维护任务记录、整合成果和核对交付。

| 位置 | 正式用途与写入时机 |
| --- | --- |

## Planning 三份文件怎么记

荔枝持续迭代，三份 Markdown 文件的入口长期保留。新阶段沿用同一组文件。能当场完成的小事，可并入所属阶段的一条摘要。

| 文件 | 它回答的问题 | 写什么，什么时候更新 |
| --- | --- | --- |
| `task_plan.md` 任务计划 | 还要做什么？ | 每件已确定的事写目标、验收条件和下一步。已排期但尚未开工的事只放这里；插单时调整先后顺序，保留原事项。 |
| `findings.md` 关键发现 | 接手人需要知道什么，凭什么？ | 只在发现会改变做法、影响验收或避免重复排查时写。每条写清结论、依据或证据位置、适用范围。推测写“待验证”。已有正式说明就指向原文。 |
| `progress.md` 进展摘要 | 已经开工的每件事做到哪了？ | 与计划用同一个事项名称。每件仍需接手的事各留一条，写实际结果、验证范围和证据位置。暂停时补停点和恢复条件；插单另起一条，恢复或有新结果时更新原条。 |

**写多细的判断。** 设想明天换人：少了这句话，他会找错文件、误判完成、重复排查，或不知道如何继续吗？会，就写清；其余操作细节省略。代码差异交给 Git，必要测试证据放对应测试或交付位置，摘要给出入口。临时下载、截图和试制文件放任务专属临时目录，验收后只保留有复验价值的材料。口令、签名私钥和真实用户资料由负责人在私有环境保管。

## 完成的东西去哪

1. **部分通过或暂时停工。** 对照计划中原定的验收条件。只通过一部分，就在该事项进展中写明已验、待验和恢复条件，保留待办。调整验收范围由负责人决定。
2. **验收通过或负责人取消。** 主写人在[阶段归档](../.planning/lychee/阶段归档/)当月的 `YYYY-MM.md` 写一条摘要。通过的写日期、事项、结果、验收范围和证据位置；取消的标明“已取消”，写负责人决定的原因、已做部分及遗留影响。确认可追溯后，只从计划和进展移除这一项。若重开，在当前计划另立条目，引用旧归档。没有在办事项时，进展留一句当前状态。
3. **整理本阶段的发现。** 仍影响其他在办工作的结论留在 `findings.md`；长期有效的结论移入对应正式文档；仅对当时版本有效的结论随本阶段归档。移走结论后，当前工作仍需引用它时只保留链接。

**插单示例（假设场景）**

| 时点 | 当前计划 | 当前进展 | 当月归档 |
| --- | --- | --- | --- |
| 安卓等真机，Windows 急件刚排入 | 安卓选图待真机验收；Windows 缩放待开工 | 安卓：模拟器通过，拿到真机后复验 | 暂无 |
| Windows 已开工 | Windows 优先；安卓验收条件照旧 | 安卓：仍等真机；Windows：已复现，正在定位 | 暂无 |
| Windows 达到原定验收条件 | 安卓选图待真机验收 | 安卓：仍等真机 | Windows：验收通过，附版本和复测证据 |

## 谁可以改

- 负责人确定管理规则及其变更，决定重要资料的删除或覆盖、对外推送、签名、正式部署和生产数据操作。按当次授权执行。
- 当前主写人统一维护项目的三份记录，负责阶段归档和交付整合。其他执行者只改分给自己的文件，将结果和证据位置交回主写人；同一文件同时只有一位主写人。
- 已授权的普通本地修改、验证和本任务临时物清理由执行者完成。交付前从正式入口检查文件、链接和验证结果。当前事实只维护一份，其余位置引用它。
