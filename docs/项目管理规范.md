# 荔枝项目管理规范

从[根目录接手入口](../AGENTS.md)进入。项目负责人决定目标、优先级和采用的版本。每项任务指定一位主写人；只有一个执行者时，由该执行者维护任务记录、整合成果和核对交付。

| 位置 | 正式用途与写入时机 |
| --- | --- |

## Planning 三份文件怎么记

荔枝持续迭代，三份 Markdown 文件的入口长期保留。新阶段沿用同一组文件。能当场完成的小事，可并入所属阶段的一条摘要。

| 文件 | 它回答的问题 | 写什么，什么时候更新 |
| --- | --- | --- |
| `task_plan.md` 任务计划 | 还要做什么？ | 写当前及已确定的待办阶段、目标、验收条件和下一步；确有阻塞时写恢复条件。阶段归档后移出当前计划。 |
| `findings.md` 关键发现 | 接手人需要知道什么，凭什么？ | 只在发现会改变做法、影响验收或避免重复排查时写。每条写清结论、依据或证据位置、适用范围。推测写“待验证”。已有正式说明就指向原文。 |
| `progress.md` 进展摘要 | 当前阶段实际交到了哪？ | 只保留当前阶段的接手摘要。取得实质进展、遇阻或暂停时，直接更新这段，写清已做到哪、还有什么缺口，以及相关证据在哪。连续小修改合为一句。阶段结束按下文归档。 |

**写多细的判断。** 设想明天换人：少了这句话，他会找错文件、误判完成、重复排查，或不知道如何继续吗？会，就写清；其余操作细节省略。代码差异交给 Git，必要测试证据放对应测试或交付位置，摘要给出入口。临时下载、截图和试制文件放任务专属临时目录，验收后只保留有复验价值的材料。口令、签名私钥和真实用户资料由负责人在私有环境保管。

**例如，假设在做安卓选图。** 计划写“下一步在厂商真机选一张照片，验证返回编辑页后能看到预览”；发现写“模拟器结果只覆盖模拟器，尚需验证厂商相册返回行为”，并给出依据；进展写“选图后失去预览的问题已修，模拟器通过，停在真机复验”，附对应版本和测试位置。这是写法示例。

## 完成的东西去哪

1. **做完一步**，从待办移走；如果结果影响当前阶段的接手，更新 `progress.md` 的当前摘要。
2. **一个阶段验收完成**，主写人把该阶段摘要从 `progress.md` 移入 [阶段归档](../.planning/lychee/阶段归档/) 的 `YYYY-MM.md`（按完成月份，有记录时才创建）。一个阶段一条，写日期、阶段名、交付结果、验收范围和证据位置；只有影响后续时才补决定及原因。同月的阶段合用一份文件。确认摘要和证据可查后，从计划移除已完成阶段，用新阶段的接手摘要替换旧进展。跨阶段仍待跟进的问题随当前记录保留。
3. **暂时停工或仍待验收**，`progress.md` 留下真实停点和缺口，计划写恢复条件与下一步。上一阶段已完成、下一阶段尚未选定时，进展只留这个状态。长期工作目录始终保留。

## 谁可以改

- 负责人确定管理规则及其变更，决定重要资料的删除或覆盖、对外推送、签名、正式部署和生产数据操作。按当次授权执行。
- 当前主写人统一维护项目的三份记录，负责阶段归档和交付整合。其他执行者只改分给自己的文件，将结果和证据位置交回主写人；同一文件同时只有一位主写人。
- 已授权的普通本地修改、验证和本任务临时物清理由执行者完成。交付前从正式入口检查文件、链接和验证结果。当前事实只维护一份，其余位置引用它。
