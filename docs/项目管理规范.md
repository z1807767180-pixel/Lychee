# 荔枝项目管理规范

从[根目录接手入口](../AGENTS.md)进入。项目负责人决定目标、优先级和采用的版本。每项任务指定一位主写人；只有一个执行者时，由该执行者维护任务记录、整合成果和核对交付。

## 文件放哪里

| 位置 | 正式用途与写入时机 |
| --- | --- |
| [AGENTS.md](../AGENTS.md) | 新会话的阅读顺序、任务入口和项目特有的验收要求。入口变化时更新链接。管理规则正文只在本文件维护。 |
| [README.md](../README.md) | 面向使用者的当前版本和使用入口。发布或下载位置变化时更新。 |
| [项目交接](项目交接.md) | 各端发布状态、实测环境、验收缺口和已确认的产品约定。由任务主写人在发布或取得新验收证据时更新相应条目。待开发的想法进入获准任务的计划。 |
| [源码接手说明](../source/接手说明.md)、[源码](../source/) | 开发方法写在接手说明。共享客户端改动按构建入口定位到原始网页或 `client/`；Windows、安卓、手机网页和 iOS 分别进入 `desktop/`、`android/`、`mobile-web/`、`ios/`。服务端在 `server/`，回归测试按工程放在 `test/` 或对应平台。生成文件可从源文件重建。 |

## Planning 三份文件怎么记

荔枝持续迭代，三份 Markdown 文件的入口长期保留。新阶段沿用同一组文件。能当场完成的小事，可并入所属阶段的一条摘要。

**什么时候记、谁来记。** 开工前，主写人先从现有计划确认本阶段要交什么、怎样算做完，有缺口就补上。每到阶段完成、暂停或换人，实际执行者先交代结果、验到哪里、成果入口及剩余事项，主写人当场更新对应记录，再进入下一阶段或报告完成。协作时由 Router 核对记录与交付一致，无须重复测试。接手必需的私有材料只记负责人、受控取用方式和是否验证可用；暂未确认就写明缺口。

一批任务收尾时，将已验收阶段的摘要移入当月归档，计划与进展只留仍需接手的事项。若对外版本、使用入口或验证边界发生变化，同步更新首页和项目交接。每项事实只维护一处，其他文件引用它。

| 文件 | 它回答的问题 | 写什么，什么时候更新 |
| --- | --- | --- |
| `task_plan.md` 任务计划 | 还要做什么？ | 每件已确定的事写目标、验收条件和下一步。已排期但尚未开工的事只放这里；插单时调整先后顺序，保留原事项。 |
| `findings.md` 关键发现 | 接手人需要知道什么，凭什么？ | 只在发现会改变做法、影响验收或避免重复排查时写。每条写清结论、依据或证据位置、适用范围。推测写“待验证”。已有正式说明就指向原文。 |
| `progress.md` 进展摘要 | 已经开工的每件事做到哪了？ | 与计划用同一个事项名称。每件仍需接手的事各留一条，写实际结果、验证范围和证据位置。暂停时补停点和恢复条件；插单另起一条，恢复或有新结果时更新原条。 |

**写多细的判断。** 设想明天换人：少了这句话，他会找错文件、误判完成、重复排查，或不知道如何继续吗？会，就写清；其余操作细节省略。代码差异交给 Git，必要测试证据放对应测试或交付位置，摘要给出入口。临时下载、截图和试制文件放任务专属临时目录，验收后只保留有复验价值的材料。口令、签名私钥和真实用户资料由负责人在私有环境保管。

## 完成的东西去哪

1. **部分通过或暂时停工。** 对照计划中原定的验收条件。只通过一部分，就在该事项进展中写明已验、待验和恢复条件，保留待办。调整验收范围由负责人决定。
2. **验收通过或负责人取消。** 主写人在[阶段归档](../.planning/lychee/阶段归档/)当月的 `YYYY-MM.md` 写一条摘要。通过的写日期、事项、结果、验收范围和证据位置；取消的标明“已取消”，写负责人决定的原因、已做部分及遗留影响。确认可追溯后，只从计划和进展移除这一项。若重开，在当前计划另立条目，引用旧归档。没有在办事项时，进展留一句当前状态。
3. **整理本阶段的发现。** 仍影响其他在办工作的结论留在 `findings.md`；长期有效的结论移入对应正式文档；仅对当时版本有效的结论随本阶段归档。移走结论后，当前工作仍需引用它时只保留链接。

**插单示例（假设场景）**

| 时点 | 当前计划 | 当前进展 | 当月归档 |
| --- | --- | --- | --- |
| 安卓等真机，Windows 急件刚排入 | 安卓选图待真机验收；Windows 缩放待开工 | 安卓：模拟器通过，拿到真机后复验 | 暂无 |
| Windows 已开工 | Windows 优先；安卓验收条件照旧 | 安卓：仍等真机；Windows：已复现，正在定位 | 暂无 |
| Windows 达到原定验收条件 | 安卓选图待真机验收 | 安卓：仍等真机 | Windows：验收通过，附版本和复测证据 |

## 一批更新怎样发布

**版本号怎么写。** Windows 版用大写 `W`（如 `W7.0.1`）。移动版用大写 `V`（如 `V7.0.2`），包括 iPhone 和安卓使用的手机网页，以及安卓 APK。公告和发布记录在移动版本号旁标明实际发布范围，例如“V7.0.2（仅手机网页）”“V7.0.2（仅安卓 APK）”或“V7.0.2（手机网页和安卓 APK）”。各自的当前版本以实际发布的网页或安装包为准。

1. **先定范围。** 同一个需求写一次目标和验收条件，列清受影响的端。共用功能开发一次，系统通知、手势、安装升级等平台差异分别适配。只改手机网页，就只发布网页。
2. **预览和正式发布分开。** “先给我看”交可体验的候选版。“这批做好就发”授权本批指定端的常规发布步骤，执行者负责跟到用户实际能拿到新版。新增平台、费用或生产数据操作另按授权处理。
3. **发布时主动升版本、写公告。** 同批小修改合并发布。每个要发布的端从自己的上一正式版递增，用户看到的版本与实际产物一致。用简单的话写一条本批变化，保留历史。同一账号标为已读后可在设置回看，新公告单独提醒。手机网页版的版本和公告由同一份[发布记录](../source/mobile-web/releases.json)生成，具体步骤见[手机网页发布说明](../source/mobile-web/README.md)。
4. **从使用者入口收尾。** 网页检查原网址是否已经提供新版本，Windows 核对发布的 EXE/MSI，安卓核对可覆盖升级的签名 APK。只检查本批发布的端。某端尚未上线或待真机体验，就在[项目交接](项目交接.md)写明该端状态。

## 怎样省步骤和额度

- **范围清楚就做完。** 沿用已确认的决定和相关记录。简单修改直接实施；协作时由 Worker 主做、Router 整合。遇到会改变结果的选择或确需授权的操作，再把具体问题交给负责人。
- **按改动大小验证。** 小修从用户实际入口核对受影响的行为，通过即收尾。已有证据仍适用就复用。涉及账号隔离、数据、签名或升级时，补查相应风险。负责人指定自己体验的项目写“待体验”。
- **有新信息再汇报。** 常规过程合并写成简短结果。遇阻先查明卡在哪、已试过什么、谁能解除；确需点击批准时给出实际入口。相同条件下避免重复读取、重复试验或让多个执行者重做同一件事。

## 谁可以改

- 负责人确定管理规则及其变更，决定重要资料的删除或覆盖、对外推送、签名、正式部署和生产数据操作。按当次授权执行。
- 当前主写人统一维护项目的三份记录，负责阶段归档和交付整合。其他执行者只改分给自己的文件，将结果和证据位置交回主写人；同一文件同时只有一位主写人。
- 已授权的普通本地修改、验证和本任务临时物清理由执行者完成。交付前从正式入口检查文件、链接和验证结果。当前事实只维护一份，其余位置引用它。
