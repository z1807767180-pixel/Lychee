# 共用服务与接手操作

Windows、手机网页和正在准备的 Android App 共用一套账号和业务服务。本地服务默认监听回环地址，可用全新的 SQLite 数据目录体验。正式服务使用 Turso；线上凭据由服务管理员保管。

## 本地试运行

在本文件上一级工程根目录运行 `python build.py`，然后在 PowerShell 设置以下本地参数并启动。

```powershell
$env:LYCHEE_DATA_DIR = Join-Path $PWD '.local/demo'
node server/index.mjs
```

默认手机入口为 `http://127.0.0.1:10000/mobile/`，桌面网页布局在 `/windows/workspace.html`。关闭服务后，下次沿用相同目录可读回测试账号和园数据。SQLite 账号账本和各园业务库都在数据目录。应用运行中的数据库备份应使用 SQLite 在线备份接口，或停服务后在保留 WAL 一致性的条件下完整备份目录。

## 真实服务拓扑

正式共存监听器由 `compose-original.mjs` 在原 6.3.3 入口基础上生成。原签名下载与旧路由继续由旧处理器处理。新协议经过 `coexist.mjs` 转入账号、园成员与业务模块。旧园沿用原 Turso 业务表。新园表按园隔离，系统账号、成员资格、邀请、公告及每日额度单独存储。私有园请求需通过登录、成员资格与绑定账号检查。发布时应保持服务端的域名、Cookie 和真实 TLS 设置一致。

正式连接参数 `TURSO_DATABASE_URL`、`TURSO_AUTH_TOKEN`、供应商密钥与运营验收的短期随机种子都只从运行环境注入。环境变量名和开关见 `index.mjs`、`provider-config.mjs`、`coexist.mjs`、`turso-migrate.mjs` 与 `server-acceptance.mjs`。首次搭建请保持真实 AI 关闭，用回环测试供应商验证。应用端只获取服务能力、业务结果与账号余额。

## 迁移、发布与恢复

1. 选定维护窗口，确认现有服务和 Turso 的独立恢复点。保存原发布的代码分片、签名清单、原安装包以及数据库备份。将这些私有恢复物放在受限备份位置。
2. 先在隔离数据库运行迁移检查和重复迁移测试。原账号使用原凭据映射，旧圈子保留原表。启用额外的导入或角色升级，需明确选择对应操作。数据库变更及哪些操作只读可直接核对 `turso-migrate.mjs`、`legacy-managers.mjs`。新加入成员沿用普通成员角色，园名、简介与园邀请码只对该园成员开放。
3. 持有私有交接归档的维护者可用 `python server/package-overlay.py <原交接归档> <受限输出目录>` 离线生成候选、原版本回退分片及摘要。它会检查原包、原服务和原业务源的摘要；公开源等价重建前端无需这些分片。对照历史 SHA、以授权测试园核对注册、账号重登、业务读回与跨园隔离后，再决定是否部署。
4. 服务代码回退时恢复管理员保管的前一组完整分片和开关，验证原版签名下载及旧园读写。数据恢复单独处理；回退代码不会回滚已经提交的新业务数据。在正式库上实施任何数据还原之前，保存故障现场和新增记录并在副本排演。
5. 已安装 Windows 6.4.x 触发 MSI 大版本降级保护时，先退出应用，使用 Microsoft 的卸载入口移除较新安装包，再装指定旧版。一般体验可在单独目录运行免安装版。应用会话数据与程序分别保存；恢复会话时需原 Windows 用户配置。原 4.1.7 程序、签名文件和更新通道独立。

## 验证边界

正式环境曾使用独立园分别完成实际问答、实际生图和海龟汤主持各一次，另有只读相册和额度验收。日常测试使用临时账号与模拟供应商。重新运行真实供应商链路可能产生费用；对日常改动优先运行 `test/provider.test.mjs` 与 `test/ai-quota.test.mjs`。
